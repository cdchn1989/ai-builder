## Decisiones
- **Rutas/lecturas:** los puertos no tenían operaciones de listado; se ampliaron (aditivo, sin tocar dominio previo). `GET /users` ordena HR primero y `GET /rooms` por nombre en el caso de uso, no en SQL, para que sea testeable.
- **Día de negocio:** `?date=YYYY-MM-DD` se interpreta en UTC-6 (misma convención que los tests de T-04) mediante `BUSINESS_UTC_OFFSET`.
- **Códigos:** esquema Zod/JSON malformado/`date` inválida → 400; `x-user-id` ausente o desconocido → 401 (extra a la spec, necesario para el middleware); `DomainError` → 403/404/409/422; resto → 500 sin filtrar detalles. Cuerpo de error uniforme `{ error: { code, message, details? } }`.
- **Auth solo en mutaciones** (POST/PATCH/DELETE), como indica la spec §5; las lecturas son abiertas.
- **WS:** `WsNotificationAdapter` depende de un objeto con `clients` (testeable con dobles) y `attach(server)` crea el `WebSocketServer` en `/ws` sobre el mismo servidor HTTP. Falla de un cliente no corta el broadcast.
- `createApp` recibe dependencias por inyección (hexagonal); `main.ts` es la única raíz de composición.
- Ruta desconocida bajo `/api/v1` → 404 JSON.

- `npm test`: api 152/152, shared 30/30, web 1/1. `npm run typecheck` sin errores.
- `docker compose up --build` con Postgres real: health 200; `GET /users` (HR primero), `/rooms`, `/reservations?date=`; POST sin cabecera → 401; flujo crear (201) → duplicado (409) → HR mueve (200, `movedByHr: true`) → cancelar (200); un cliente `ws://localhost:3000/ws` recibió un `DATA_INVALIDATED` por cada mutación.
